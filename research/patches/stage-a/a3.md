## What it does

`ApplyGraphicsRegisterPacket` folds every SET_*_REG packet into a running checksum. That runs on stage A
(`gfx_reg_checksum`) and again on the draw-preparation scanner and each worker (`vk_draw_prep.cpp`). A prepared draw
is used only when its checksum equals stage A's. The fold is a dependent chain (xor, 64-bit multiply, xor-shift;
about 6 cycles a word on Zen 2). With A3, `Liverpool::HashRegisterPacket` uses `HashWordsPaired`: two words per step
(`(c ^ (w0 | w1 << 32)) * K`, then `c ^= c >> 32`; an odd last word as before). That is half the steps. The one-word
`HashWords` is the old loop, moved to `gow3_stage_a.h`.

## Invariants

- Every thread that produces or compares the checksum goes through `Liverpool::HashRegisterPacket`. That covers
  stage A's `ApplyGraphicsRegisterPacket`, the compute-queue SetShReg mix (`gfx_reg_checksum ^ 0xA5C0...`), and the
  scanner and workers, which call the same static `ApplyGraphicsRegisterPacket`. The compares are in
  `vk_pipeline_cache.cpp` (`prepared.reg_checksum != liverpool->gfx_reg_checksum`) and `Rasterizer::Draw` (the
  `match` count). A hash computed anywhere else with the other fold makes prepared draws miss: correct, but slower.
- Each step is still a bijection of the 64-bit state. A false match needs a 64-bit collision, as before.
- `PairedRegisterHash()` reads the toggle bit on every call, so a live flip changes the fold on stage A and on the
  scanner at different stream positions (the scanner runs ahead). Their running checksums then differ for good:
  every step is a bijection, the scanner carries its own chain (`start_checksum` / `end_checksum`, `tail_checksum`
  from `Collect`), and `DrawPreparation::BeginSubmission` seeds it from stage A only at the first submission or on a
  rebase (scanner more than 64 submissions behind). So after the first flip **no draw is prepared for the rest of
  the launch**, in either state (correct, slower). The impl doc and the comment above `PairedRegisterHash` say "until
  the next submission seeds the workers"; the code did not do that. **Since `adfeb67` A3 is restart-only:**
  `PairedRegisterHash()` returns the start value of `GOW3_REG_HASH_PAIRED` and no longer reads the bit, so the fold
  can never change mid-launch. Making it live again needs a reseed when the fold changes (a forced rebase).
- `toggle2:PairedRegisterHash` (4194304) is reserved and not read: old toggle states with 7340032 now switch A1 + A2
  only. Do not reuse the bit for something else while old step scripts and docs still write it.
- The checksum values change, not their use. Nothing may persist them across launches or compare them with a value
  made by another build.

## Interactions

- lineage-draw-preparation: the prepared-draw match is the only consumer. Watch "Draw preparation: N prepared
  pipelines used, M not": a drop with A3 on would mean the two sides disagree.
- A1, A2: measured only together (live bits 7340032), all in the Deck preset. A1 + A2 alone live: 3145728.
- Not rescore A3 (stage-b-core). The IDs collide.

## Evidence

- Measured only as part of A1-A3. Round 1, launch 7 (Deck, 2026-11-05): 78.1 vs 77.5 FPS, lows equal. At 1,200 MHz:
  +0.65 FPS. Launch 15: A1-A3 off cost +9.9 points of a core at the 60 cap.
- `stage-a-hash-test`: the one-word hash equals the old loop on 100,000 random packets. Both hashes tell apart every
  one-bit flip and neighbour swap, and 2 million near-identical variants (0 collisions). 0.63 vs 1.03 ns a word on
  the 7800X3D (-38%).
- The prepared-share check from the impl doc was not written up, and the logs fail it. In
  `data/deck-stagea-1.log` "Draw preparation" goes from 70-98% prepared (most windows about 90%) to **0 prepared**
  at the first `(A3 toggled off)` window (lines 2625 -> 2646) and stays 0 in both states, 0 scanner rebases. Launch
  15 the same (from lines 9198 and 20691). So the A1-A3 A/Bs above compared both states mostly without draw
  preparation, and so did every later live A/B in those launches (Launch 15's drain-hybrid, R1/R2/T1/T2 and
  signal-sleep rows). [log; cause from the code]

## History and pitfalls

- Expected about -0.06 to -0.1 ms of stage A a frame, and about as much again on the scanner and workers (inferred).
- Opt-in on Windows, and not measured on the PC.
- The Deck preset sets `GOW3_REG_HASH_PAIRED=1` at start and never flips it, so normal play kept draw preparation.
  Only live A/Bs of bit 4194304 (or of 7340032) hit the dead-preparation state above; fixed by `adfeb67`
  (restart-only). An A3 A/B is now a restart pair.
