## What it does

`RegDirty::blocks` was a `std::bitset<1664>` (one bit per 32-register block). On glibc, `Rasterizer::PostDraw` walked
it with `_Find_first` / `_Find_next`. libc++ (the Windows clang64 build) has neither, so the fallback tested all 1,664
bits on every draw with any block set. It is now `RegDirty::Blocks`: 26 `u64` words, with a `ForEach` that visits the set blocks with
`std::countr_zero`. `PostDraw` and `RegDelta::Capture` use `ForEach`. Same blocks, same order, no switch.

## Invariants

- `NumBlocks` (`Regs::NumRegs` 0xD000 / 32 = 1,664) must fit in `NumWords * 64`. Today that is exactly 26 words,
  with no spare bits. `Blocks::set` does not check bounds (`std::bitset::set` threw), so every caller must go through
  `RegDirty::Mark`, which clamps to `NumRegs`. A direct `blocks.set(n)` with n >= 1,664 writes past `words`.
- `ForEach` visits blocks in ascending order, as the old loop did. `PostDraw` writes the block list and its
  register words in one pass, and so does `RegDelta::Capture` (`blocks` and `words`), so each list stays paired.
  Stage B and the preparation workers apply them in that layout.
- `reset()` clears every word. `PostDraw` calls `dirty.Clear()` before each `Commit` (and when it first syncs
  `pipe_regs`); the scanner clears its own `RegDirty` per submission (`vk_draw_prep.cpp`). A block left set only means
  extra copying (of current values), never a wrong register. A block *missed* would leave stage B with a stale
  register, so `ForEach` must visit every set bit.

## Interactions

- lineage-draw-pipe: the dirty blocks are how stage A sends the registers to stage B per draw (`PostDraw`).
- lineage-draw-preparation: `RegDelta` (in `vk_draw_prep.h`) is the scanner's per-draw register delta. It uses the
  same `ForEach`.
- `PostDraw`'s part is neutral on Linux / glibc, where `_Find_first` already skipped empty words; the measured gain is
  the libc++ (Windows) build. `RegDelta::Capture` tested all 1,664 blocks on every library before (no `_Find_first`
  branch), so the scanner gains on Linux too (not measured).

## Evidence

- WPR trace heavy-v3 (before the fix, 4K heavy view, about 2,800 draws a frame): stage A (`GpuCommandProcessor`) at
  0.91 core, with `std::bitset` test / ref at 13.1% of it. Stage A was the bottleneck.
- T-P1 (2026-10-18, build `5cd037e`, launched by Claude with the user's go): heavy view at 124-131 FPS, against
  114-123 in T-V3 (about +8%). The user: "1% lows are improved".
