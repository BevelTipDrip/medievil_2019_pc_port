## What it does

`Liverpool::ProcessCommands` (stage A, the GPU command thread) runs the callbacks guest threads queue with
`SendCommand`: readbacks (`DownloadMemory` records a copy and `Finish()`es), `ResolveReadbacks`, non-EOP flips.
It now calls `DrainDrawPipe(ReasonCommands)` inside the `while (num_commands)` loop, before each command is popped
from `command_queue`, instead of once when the first check saw a command. The drain returns at once when stage B
is idle (`DrawPipe::Drain`: `consumed == head`). Same change as the Bloodborne port's 0.3.

## Invariants

- Every queued command runs with stage B idle, so only one thread records into the scheduler. The drain must stay
  inside the loop, before the pop. Moved back out, a command queued between the check and the loop runs beside
  stage B again: H1 (hang in `WaitHostCopies`, host copies left in an unqueued chunk) and C1 (a draw's buffer binds
  in one command buffer and its `drawIndexed` in the next: NVIDIA driver crash in `vkCmdDrawIndexed`).
- `num_commands` is atomic and grows from any thread (`SendCommand` in `liverpool.h`, under `submit_mutex`). Only
  stage A pops (`ProcessCommands`, called from `Process` and per packet in `ProcessGraphics`, `ProcessCeUpdate` and
  `ProcessCompute`).
- Guest-thread work that records into the scheduler must go through the command queue. `Rasterizer::ReadMemory`'s
  own drain does nothing off stage A (`DrainDrawPipe` returns unless `OnStageA()`), so this loop is the only drain
  for faults posted with `assume_locks=false` (`GuestFaultSignalHandler` passes `IsGpuSideThread()` as
  `assume_locks`; `ResolveReadbacks` and `BufferCache::ReadMemory` then `SendCommand<true>`).
- Without a draw pipe (`GOW3_DRAW_PIPE=0`, or fewer than 8 hardware threads when unset: `DrawPipeWanted`),
  `DrainDrawPipe` returns at once, so the patch costs nothing there.

## Interactions

- lineage-draw-pipe: the race exists only with the two-stage pipe (`GOW3_DRAW_PIPE=0` ran clean in T-race).
- upstream-record-data-fix: upstream's `SyncWithDrawRecorder` / `RecordData` order is a separate guard for stage A
  recording while stage B has queued draws. They complement each other (fix-inventory section 8), neither replaces
  the other.
- L4 (re-kick in `WaitHostCopies`, reverted in `a07f709`) treated the H1 symptom. L5 removed the cause. Under the
  race, L4's re-kick could turn the hang into the crash.
- drain-hybrid / drain-sleep: these change how each of these drains waits, not whether it drains.
- decode-pacing removes the idle drain at the end of queued work. The per-command drain here stays, so a command
  arriving while stage B still records the previous frame waits for it.
- crash-dump was added the same day to catch C1 if it came back.

## Evidence

- T-race (2026-10-18, `GOW3_DRAW_PIPE=0`, Graveyard idle): no fault in about 9 minutes. With the pipe on, the same
  scenario froze at about 2 minutes (H1) and crashed at about 4 (C1).
- T-L5 session 1 (build `bc0e1d6`, pipe on, 4K, Graveyard): no fault and no freeze in about 19 minutes, clean exit. The
  user: "a pretty long run, no crashes". FPS median 102.3 (pipe-off run 85.2), p99 median 13.53 ms. Cost: about 37
  `commands` drains a second, 0.1% of stage A. The doc wanted one more session before calling it verified.
  fix-inventory (2026-11-02): no C1 / H1 since.

## History and pitfalls

- Found by reading the code (the root-cause section), then matched to Bloodborne 0.3's `4d4d208`. Bloodborne's comment
  names "null chunk crashes …, lost chunks, hangs".
- Still open: stage B can fault on a guest read between its buffer binds and the draw (motion-vector hashing of bone
  palettes). That runs the readback inline. It exists with the pipe off too. Possible fix: emit the binds after that
  block.
- Not to confuse with the Deck plan's item L5 (the AvPlayer join hang, card avplayer-join-hang), or with T-L5 in
