## What it does

On Linux each pool commit / decommit (~6,000 a second) made its `mmap` / `munmap` with the table lock held
exclusively; every locked reader (backing-view copies, labels, GPU page protection) waited behind the address-space
lock and TLB shootdowns. Now (`pool_commit_unlocked`): take pages (locked), `host_map_unlocked` over the reserved range
(unlocked), `record_mapped` + map hook (locked). `pool_decommit_unlocked`: enter the range as reserved + unmap hook
(locked), one reservation `mmap` replaces the view (unlocked; was `munmap` + `mmap`), then give or keep the pages
(locked). `pool_map_mutex` serializes pool commits / decommits as the table lock did. Second toggle word 256: host calls
under the lock again (live, chosen per call).

## Invariants

- The table never says mapped where the host is not: a commit enters its range only after `host_map_unlocked`
  succeeded (until then it reads reserved, as the guest expects until the call returns); a decommit enters reserved
  before the host view goes.
- Pages return to the pool (`pool_keep_locked` / `pool_give_locked`) only after the reservation `mmap` succeeded; if
  it fails they stay taken (a leak, never a second mapping of live pages).
- `pool_map_mutex` is held for the whole step by both the unlocked and (since `1b3c28b`) the locked pool paths; lock
  order `pool_map_mutex` then the table lock, nothing takes them the other way. Without it, a bit-256 flip between two
  calls could let a locked commit lose its mapping to an unlocked decommit's reservation.
- If the decommit's `record_mapped` fails, `drop_range` has already freed the range in the table: the reservation
  `mmap` then stays under the table lock so no other map takes the range first (`1b3c28b`).
- L2's rule holds through `record_mapped` (its `vma_erase` / `vma_insert` bump the buckets before the host change).
- Kept-page handling (`pool_take_kept_locked`, `pool_zero_foreign_locked`, discard after a failed commit) stays in
  the locked steps; non-pool kinds in a decommit range take the old all-locked path.
- Windows: `pool_maps_unlocked()` is 0 (the host views table `regions` is shared state).

## Interactions

- pool-kept-pages: shares both paths; D4 only changed locking and is not the cause of the Mausoleum leak.
- A1: correct with D4 because the backing view does not change outside the lock; table and pool pages change only in
  the locked steps. One exception: with `GOW3_POOL_ZERO_DECOMMIT=1` (diagnostic, off) the decommit's `host_discard`
  runs between the locked steps, after the table already says reserved and while the pages are still taken.
- D5: with the host calls out, table lock holds are short, which is what makes D5's spin worth it.
- pool-prefill: `pool_populate` runs after both locks are released and before `flush_hooks`, in both paths.
- copy-thread-backing-view: Linux GPU copies read the backing view, so a view vanishing outside the lock is harmless.

## Evidence

- Deck baseline 1 (AppImage `a863482`, live pair `0 256`, 20 s x 3): 73.5 FPS with D4 off vs 74.2 base, stage B
  92.8% vs ~94%: +0.7 FPS, noise level. No visual issues reported in that run.
- Origin claim (spacepepperoni message): heavy view 68.5 -> 75.8 FPS, likely a desktop at 1440p.
- An independent review (2026-11-04) found no real race; its two edge cases are `1b3c28b`.

## History and pitfalls

- By Porticus (upstream PR #57, `a61aab3`), ported from spacepepperoni's reapply `a3f4c1d` (GPL-2.0) and adapted
  (seqlock table, L2 buckets, Windows kept views).
- Older and unchanged: `flush_hooks` can return before hooks another thread dequeued have run, so a decommit then
  recommit of one range can run MAP while UNMAP still runs elsewhere (impl-stage-b-bundle-2.md review).
- The decommit's `recorded` holds `record_mapped`'s error code (0 = entered), so `if (!recorded) write_unlock()` is
  the normal path; read it that way before touching the lock juggling.
- The re-score's alternative ("L2 keep views on Linux") was not built; pool-kept-pages keeps pages, not views.
