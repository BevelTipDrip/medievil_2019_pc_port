## What it does

Design only, nothing built. On Linux + RADV integrated GPUs, guest direct memory would be allocated as Vulkan memory
(Deck type 5, `HOST_VISIBLE|HOST_COHERENT|HOST_CACHED`), exported as dma-buf, mapped by the runtime at the guest
addresses instead of the memfd, and bound in place into the buffer cache's sparse arena. Buffers would be read and
written where the game keeps them: no uploads, write tracking or downloads. Images stay images. Precondition: guest
fences signal in GPU order (U5-2). Gate 2 stopped it at that precondition (no-go as designed); a hybrid is open.

## Invariants

What a rebuild must keep true (the design's own rules; none is in the code today):
- Data the GPU reads in place must not be rewritten by the guest until the GPU read it. The copy model is safe today
  only because stage B snapshots buffers (stream copies, host copies before the submit). With the frame label signalled
  early the RHI records ~2 frames deeper than on the PS4. Study-eop-wait-site.md section 4 (frame EOP at stage B,
  `frames_queued=1`): RHI-thread pool data (guest 0x5805e70, 4 slots) is safe with no frame to spare, render-thread
  data in that slot can race by 1 frame [inferred], `frames_queued` 0 or >= 2 breaks the pool, and the two
  flush-and-rewind paths (spin labels at stage B) are unsafe whenever they run.
- That table predates early-frame-eop + decode-pacing (Deck preset: label at decode, lead 2, "retired" = stage B
  passed, not the GPU). In place, the GPU's lag behind stage B adds to that lead: redo the margins before any hybrid.
- The copy-model guards must be bypassed for in-place ranges, not left on: D2 precise writes, gpu-write-twins and S2's
  upload-once path would write staged bytes over newer in-place bytes.
- GPU idle must not come before late labels: the guest frees the objects holding fence labels at GPU idle
  (`liverpool.cpp` submission-end comment; Bloodborne's heap corruption, gate2-ordered-fences).
- Backing-view users (`backing_base`, `runtime_memory_write_backing` / `read_backing`, fence writers'
  `TryWriteBacking`, copy-thread-backing-view, A1's lock-free copies) need per-chunk views of the same dma-buf fds
  at `backing_base + phys`. pool-kept-pages' zeroing (Linux `host_discard`, a memfd hole punch) becomes a memset.
- Assumption (class C): integrated GPU with cached host memory at device-local read speed (gate 1), `IsIntegrated()`;
  off on Windows (no Vulkan memory at fixed guest addresses), discrete GPUs and NVIDIA.

## Interactions

- depends_on U5-2: GPU-completion fences under the copy model, the design's step 2. It failed its rule (-36%).
- conflicts_with D2, gpu-write-twins, S2: harmful for in-place ranges (design section 13); D3, fault-page-download,
  D1 become unnecessary there. uffd and hot-pages become moot for buffers.
- gate2-ordered-fences: the first, reverted try at the precondition (black screen at boot, unsafe GPU idle).
- U2 is the decision rule's fallback (direct arena writes); it ran at 62-63 FPS both ways, no gain.
- early-frame-eop and decode-pacing (both on in the Deck preset, off with `GOW3_GPU_FENCES`) came out of the user's
  direction to keep the per-frame EOP early. Their lead (decode pacing clamped 1..2, early-frame-eop default 2 with no
  upper clamp) must stay inside UE4's frame-counted recycling (3-frame label free list, 4-slot pool); at lead 2 the
  margin is already 0 for render-thread pool data under the copy model (impl-decode-pacing.md heap-safety table).
  Hybrid (B) holds the frame EOP until after the next flip, so it cannot run with early-frame-eop on.
- frames-queued-2: the study's pool margins need `frames_queued=1`; 0 or >= 2 is unsafe in place.
- Design "L2" (keep pool views on Linux, plan-linux-deck.md item list) is not the patch-map card L2 (region caches).

## Evidence

- Gate 1 (Deck probes, not the game): type 5 backs the sparse arena; GPU reads 128 MiB at 41.2 GB/s vs 40.8
  device-local. memfd import fails (`VK_ERROR_INVALID_EXTERNAL_HANDLE`); Vulkan dma-buf memory maps at guest addresses
  (512 MiB in 57.5 ms); CPU writes memfd 1.0 GB/s, dma-buf view 4.9 GB/s.
- Native runs 7-8: the "~760 faults a frame" were pages marked; real faults ~1 a frame (Garlic-WC, Onion 0), so
  faults are not a Deck cost, which removes much of U5's motivation.
- Native run 9: EOP with IRQ lag p50 14.2-14.7 ms; the game's `SubmitGPUCommandsAsyncTaskThread` waits on it ~5.6 ms
  a frame, never already signalled. Gate 2 rule (> +4 ms, newest frame, no slack): no-go as designed.
- U5-2 A/B (Deck, 67%, auto clock): 64.0 FPS fences off, 39.4 ahead 0, 41.2 ahead 2 (-36%); game EOP wait 6.2 ->
  17.6 ms; fence lag 15 -> 0.4 ms, no crash. The user: frame generation steadier, CPU use about halved, VRAM ~1 GB
  lower. B2 at a pinned 1600 MHz: ~+20 FPS over B2 at auto, heavy graveyard still behind A. U5 itself: never built.

## History and pitfalls

- The game waits once a frame on frame N-1's EOP (guest+0x68af47, SubmitEndOfFrameQueue): it gates submission and
  recycles nothing. GPU-ordered, that wait turns CPU and GPU into a relay (frame = CPU + GPU, not the max).
- No pinned GPU clock in a Deck preset: it caps the CPU at ~2 GHz and hurts the copy model.
- Retry only as the hybrid the user asked for (keep the per-frame EOP early, protect what it guards): (A) copy only
  the transient pool (hook its allocator return at guest+0x697e54) and read the rest in place, or (B) hold the frame
  EOP until stage B passes the next flip's frames-ahead wait, `frames_queued` fixed at 1. (A) also covers the rewind
  paths; (B) does not (their spin labels then need GPU order). Run study-eop-wait-site.md section 6's stats first, and read Bloodborne 0.7's rewritten
  `bbport_guest_memory.cpp` before porting. The gain left is stage B's copy work (host copies 4-5%, WRITE_DATA 3.7%).
