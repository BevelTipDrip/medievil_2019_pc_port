## What it does

1. Linux: `read_lock` / `write_lock` try the rwlock once; when it is busy, `lock_contended_path` retries up to 1000
   times with a pause before the blocking `pthread_rwlock_rdlock` / `wrlock`. A futex sleep and wake costs a Deck
   thread more than a table edit lasts and drops its core's clock. Counted with `GOW3_FRAME_STATS` (contended, ended by
   the spin, blocked ns). Windows keeps its SRW lock as it was.
2. Both platforms: `flush_hooks` returns when `pending_count` reads 0, instead of taking the table lock exclusively
   once more per map / commit / decommit / protect only to find the queue empty.
Second toggle word 512: block at once and always take the lock in `flush_hooks` (live).

## Invariants

- `pending` and `pending_count` change only under the exclusive table lock; `queue_hook` publishes the count with a
  release store, `flush_hooks` reads it with acquire. A caller that reads 0 had its own hooks taken by another flush,
  and every flush runs each hook it dequeues.
- Every operation that queues hooks calls `flush_hooks` after it releases the lock (map, flexible map, batch map,
  release, protect, pool commit / decommit; a new one that does not would leave its hooks to whichever operation
  flushes next). `direct_unmap` is the exception below.
- `direct_unmap` notifies first and restores `pending_count` under the lock; a flusher that sees the transient count
  takes the lock and waits for the restore.
- Nested reads rely on glibc's default reader-preferring rwlock granting `tryrdlock` to a thread already reading;
  a writer-preferring rwlock kind would deadlock nested reads (true before D5 too). Writer starvation is as before,
  bounded by the 1000 tries.
- The uncontended path is one trylock, as the lock call was.

## Interactions

- D4: after it the table lock covers only table and pool-page edits (microseconds), so spinning usually wins.
- lockfree-region-reads / L2: most GPU-side readers never take the lock, which is why the expected stage B gain was ~0;
  the locked readers left are A1's fallback, labels and `runtime_memory_gpu_protect`.
- stage-b-spin: a separate Deck idea (stage B spins before it blocks, second word 1024); neutral on the Deck (77.1 vs
  77.1 FPS), not in the preset; unrelated code, only the same "spin before a futex sleep" reasoning.

## Evidence

- Deck baseline 1 (AppImage `a863482`, live pair `0 512`, 20 s x 3, medians of 9 windows): D5 off 72.9 FPS vs 74.2
  base, stage B 92.0%: **+1.3 FPS for D5**, the largest of the bundle-2 pairs (single launch; within-launch drift of
  ~1.35 FPS was seen later, so treat it as small but positive). Not checked by the user on its own.
- Origin claim (spacepepperoni message): heavy view ~77 -> ~87 FPS.

## History and pitfalls

- By Porticus (upstream PR #57, `ef597f0`), from spacepepperoni's reapply `95e295e` (GPL-2.0), partly: their separate
  hook and pool spin locks were not taken, because they change who may run a hook while an operation still holds the
  table lock (map / unmap hook order) for a gain the re-score put at ~0.
- An independent review (2026-11-04) found the empty-queue check and the spin sound.
