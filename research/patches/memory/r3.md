## What it does

Each pool chunk keeps `free_hint`: every page below it is not `POOL_FREE`. `pool_take_locked` starts its scan there
and moves the hint past the run it takes; `pool_give_locked` lowers it to the first page it frees. Before, every
commit scanned the chunk's page map byte by byte from page 0 under the memory write lock. The run returned is the same
first fit as before. No switch (behaviour-identical).

## Invariants

- Every write that makes a page `POOL_FREE` must lower `free_hint` to it if it is below. Today only
  `pool_give_locked` frees, and lowers the hint only for `state==POOL_FREE`. A new free path that skips this leaves
  free pages below the hint that no take finds: lost capacity and an early `NO_MEMORY`, not corruption.
- Writes that make a page `POOL_TAKEN` or `POOL_KEPT` need no hint change (pages below stay non-free):
  `pool_take_at_locked` (M1, later; moves the hint only when it took exactly at it), `pool_keep_locked` and
  `pool_take_kept_locked` (Linux, pool-kept-pages). All page-state writes are under the table write lock.
- `pool_expand` starts a chunk with `free_hint=0`; the hint only describes `POOL_FREE`, so M1b's second loop (kept
  pages) scans from page 0 without one: under memory pressure that loop costs what the old scan did.
- Lowest-first allocation is preserved (first fit from the lowest free page): pool-prefill counts on it.

## Interactions

- R2 (rwlock hash set, runtime): built and measured together; T-R23 is their combined result.
- M1 / pool-kept-pages: added the `POOL_KEPT` state; the first loop skips kept pages and moves the hint over them.
- pool-prefill: its prefill covers the lowest physical pages because commits take the lowest free ones.

## Evidence

- Checked against the old functions on 200,000 random takes and partial gives: identical runs and page maps (scratch
  harness, not in the repo).
- T-R23 (build `2097554`, R2 + R3, Graveyard heavy view 2,600-3,100 draws, vs `wpr-graveyard`): FPS median 81.2 ->
  **94.7**, lowest window 71.3 -> 80.7, p99 median 16.7 -> 14.6 ms. WPR: `pool_take_locked` 0.3% of the busiest game
  thread (was 7.5%), gone from the pool-heavy thread (was 28.7%). The user: "the 1% lows seem much much better. When
  looking at an area that previously dropped to 50-60 fps 1% lows, it's closer to 80."

## History and pitfalls

- The first T-R23 launch exited silently with code 5 at startup (S1, plan-baseline-issues.md); the retry ran
  normally. Later S1s came with other builds (four in ~65 launches, not tied to one change); on 2026-10-30 S1 was
  found to be an access violation in winpthread's `pthread_mutex_lock` on a garbage mutex (crash-dump card), not R3.
- The comment above the old function said "longest free run"; the code was first fit, and R3 kept first fit.
