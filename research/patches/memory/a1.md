## What it does

`CopySparseSerial` (stage A's constant ring copies, stream copies, uploads) first calls `runtime_memory_copy_backing`.
It reads `table_generation` (must be even), takes the range's backing offset from the R1 index entry if one covers it
with an unchanged stamp, else does one lock-free `vma_seq` search into at most 8 pieces (mapped: backing offset; gap or
reserved: zero), bounds-checks the offsets, copies from `backing_base`, and accepts the copy only if `table_generation`
is still the same value. Otherwise it returns 0 and the locked loop (region lookup + `runtime_memory_read_backing`
under the read lock) copies as before. Opt-in `GOW3_BACKING_COPY=1`; second toggle word 1048576 off, live.

## Invariants

- Every edit that changes which backing offset an address maps to, or what a backing offset holds, is made with the
  table write lock held (`table_generation` odd): `vma_insert` / `vma_erase` / `split_at`, pool pages taken, given or
  kept (`pool_take_locked`, `pool_give_locked`, `pool_keep_locked`, `pool_take_kept_locked`), holes punched
  (`host_discard` in `direct_release`, `flex_free`, `pool_zero_foreign_locked`, a failed commit). A new edit outside
  the lock would let a copy mix old and new bytes undetected. Known exception: `GOW3_POOL_ZERO_DECOMMIT`'s
  `host_discard` in `pool_decommit_unlocked` runs after the unlock; safe only because the table already says reserved
  and the pages are still taken.
- `table_generation` is bumped on lock and on unlock (`write_lock` / `write_unlock`), so "same even value" means no
  writer section overlapped the copy.
- `backing_base` is one `MAP_SHARED | MAP_NORESERVE` view of the whole memfd for the process's life: never unmapped,
  so a stale offset cannot fault; offsets are still checked against `POOL_SIZE+FLEX_SPAN`.
- Off when `optimistic_enabled()` is false (`GOW3_OPTIMISTIC_CLAMP=0`, the menu's lock-free switch, or the caller holds
  the lock exclusively). Gaps and reserved ranges read as zero, exactly as the locked loop.
- The locked fallback must overwrite the whole destination (it does), since a rejected copy leaves partial bytes.

## Interactions

- lockfree-region-reads (search, `optimistic_enabled`), L2 / R1-region-index (stamps, the index's `phys`); without R1
  every copy does its own search.
- copy-thread-backing-view: the locked path it falls back to (Linux reads the backing view, not the guest mapping).
- D4: compatible because the backing view never changes outside the lock; D5: fewer locked readers.
- A2, A3: measured together as "A1-A3" (mask 7340032). Windows: `runtime_memory_copy_backing` returns 0 and
  `CopySparseSerial` never calls it (`#ifndef _WIN32`); Windows copies read the guest mapping after an unlocked lookup
  (the stub's "kept views": M1 with decommit-keep-access).
- pool-prefill: its `fallocate` (mode 0) runs on its own thread without the lock, but only allocates holes, which
  read as zero before and after, so no copy can see a change.

## Evidence

- Cuts redo (2026-11-07, draw preparation alive): A1 + A2 off (3145728) +2.0 points of a core at the 60 cap, +0.16 W CPU; uncapped no FPS change (82.8 / 82.8). Launch 15's A1-A3 +9.9 was mostly the dead draw preparation.
- `runtime-test --backing-copies` (WSL, 3 runs): ~30,000 lock-free copies each vs the locked loop, no mismatch,
  including copies while another thread maps and unmaps the range 300 times.
- Round 1 (GPU auto, live `0 0` vs `0 7340032`): 78.1 vs 77.5 FPS (+0.6), lows equal; A1 4,350 copies a frame without
  the lock. Round 2 (GPU 1,200 MHz): 79.25 vs 78.60 (+0.65), worst median / max 17.8 / 20.5 vs 18.2 / 22.3 ms.
- Launch 15 (60 cap): A1-A3 off costs +9.9 points of a core of process CPU (CPU power +0.00-0.03 W); uncapped 78.1 vs
  78.3 FPS (GPU-bound there). In the Deck preset since 2026-11-06.
- The picture while toggling 1048576 was asked for (A1 carries the constants); no visual check is recorded.
