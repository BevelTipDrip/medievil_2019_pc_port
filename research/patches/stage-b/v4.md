## What it does

GCN keeps a depth buffer's stencil in a separate plane at its own address. The texture cache's depth image covers
only the depth plane, so UE4's compute-shader stencil clears never reached it. Each depth bind in
`BeginRenderingFull` records its plane: `StencilAddress()`, `(tile_max + 1) * 64 * NumSamples()` bytes, in
`stencil_planes`. `NoteStencilPlaneWrites` (in `BindResources`) marks a plane when a compute dispatch writes a
buffer that starts at the plane and is within 1/16 of its size. The next bind of that depth buffer copies the plane
(`ObtainBufferForImage`) into the image's stencil aspect with `CopyBufferToStencil`.

## Invariants

- Class C: the copy is linear (`bufferRowLength` 0), with no detiling. It is exact only for a uniform fill, which is
  what UE4's stencil clear is. A non-uniform shader-written stencil would land scrambled.
- A rewrite must start at the plane and be plane-sized (`begin == plane`, size within 1/16). The first version
  counted any larger buffer spanning the plane and copied the plane at the depth address (T-V4).
- No copy when the pass clears the stencil itself (`is_stencil_clear`), for MSAA (`num_samples == 1` only), for
  reduced scene targets (`!reduced`), or with bit 59 set. Those paths keep the old behaviour. A pending mark is
  consumed (erased) at the next bind of that plane even when no copy is made, so it never applies to a later pass.
- Marks need a known plane: `NoteStencilPlaneWrites` returns at once while `stencil_planes` is empty, so a stencil
  clear before the depth buffer's first bind is not seen.
- Only compute pipelines that reach `NoteStencilPlaneWrites` count. Dispatches that `BindResources` handles first
  (`IsComputeImageCopy`, `IsComputeMetaClear`, `IsComputeImageClear`) are not seen. A stencil clear the port ever
  starts treating as one of those would lose V4.
- `CopyBufferToStencil` ends the render pass, moves the image to TransferDst and marks it `GpuModified`. The next
  attachment use must transition it back; it does (layout differs, so lean-barriers part c does not apply).
- `stencil_planes` is never pruned (one entry per distinct plane address; small in MediEvil).

## Interactions

- lean-barriers: its re-bind without a barrier (`KeepStencilAttachment`) needs DepthReadOnlyStencilAttachment.
  After a V4 copy the image is in TransferDst, so the barrier is recorded, as it must be.
- depth-write-effective decides the layout in the same block, after this copy.
- spacepepperoni's exact stencil clears (study-fork-spacepepperoni.md) touch the same state. Port them only with
  their switch and an A/B against V4.

## Evidence

- T-V4 (build `769de12`, Dan at a torch): the box is gone with V4 and comes back with bit 59 set (live A/B twice).
  The dynamic shadows near Dan vanished too, and the copies reported the plane at the depth address.
- T-V4b (build `423efc7`): menu plane 0x201a000000 right after the 32 MB depth plane, each copy after a fill of
  exactly that plane (shader 0x6846b3858ae55a9e).
- T-V4 RenderDoc (`v4-shadow_frame14784.rdc`): the shadow mask is clean. The "torch shadows" missing with V4 were the
  moon's per-object shadows leaking out of their stencil volumes, so V1 is fixed. Verified in game by the user (box
  gone, live A/B) and in RenderDoc.

## History and pitfalls

- Open item 5 (study-frame-cost, plan-work-queue): a ~0.21 ms mid-frame VRAM copy window is most likely this 4K
  stencil-plane copy [inferred, not identified]; corrected gain <= ~0.1 ms of GPU a frame. The study's fix options:
  copy only when the plane really changed, or keep the stencil in a separate S8 image (shader stencil export is
  unavailable). Measure first: `CopyBufferToStencil` has no `TransferMark` label yet (the study's "stencil plane
  copy" label is still to be added; image upload / alias copy / download have one).
- Log lines "Stencil plane copy" (24) and "Stencil plane-sized write ... (known plane ...)" (12) show where the game
  keeps its planes.
