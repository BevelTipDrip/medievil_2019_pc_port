## What it does

`GOW3_GPU_FENCES=1` (read once): end-of-pipe / end-of-shader labels, compute RELEASE_MEM labels and their interrupts
reach the guest only after the GPU executed the work before them (`Rasterizer::SignalAfterGpu`, a `gow3:GpuSignals`
thread on the timeline semaphore, in order); GPU idle and "frame retired" too. The submission lock becomes 0.7's
`decode` pacing (`Gow3GpuFences::BeginFrame` / `AfterSubmit` in gnmdriver.cpp): a frame's first `GOW3_SUBMIT_AHEAD`
(2) submissions pass, later ones and `sceGnmSubmitDone` wait for the GPU to finish the previous frame. Submitters for
urgent signals: decoder idle flush (`GOW3_SIGNAL_IDLE_US`, 200), batching at submission ends (`SubmitForSignalsNow`:
`GOW3_SIGNAL_FLUSH_US` 2000, `_IDLE_BACKLOG`, `_IDLE_FLUSH`, `_DRAIN_FLUSH`), WAIT_REG_MEM flush + yield
(`GpuOrderedWait`, `GOW3_WAIT_REG_MEM_GIVEUP_MS` 0 = never), watchdogs; `GOW3_LEAK_WATCH` / `_LIMIT_MB` watch growth.

## Invariants

- Every guest wait on a GPU-ordered signal needs a submitter; an unbounded wait for a tick nobody submits deadlocks
  at boot (the `f97479f` attempt, gate2-ordered-fences).
- GPU idle and frames retire only after the labels before them; labels are single atomic stores; a label whose memory
  was unmapped is dropped (counted).
- **Class C:** with ahead > 0 the next frame's first submissions run while frame F's labels are pending; assumes UE4
  does not free or reuse per-frame label memory then. WRITE_DATA flags and the flip interrupt still overtake labels.
- Which knobs act without `GOW3_GPU_FENCES=1` (checked in the code): none of `GOW3_SIGNAL_*`, `GOW3_SUBMIT_LOCK`
  (`LockOnGpu` needs `Enabled()`), `GOW3_LEAK_*` (only via `BeginFrame`), `GOW3_WAIT_REG_MEM_GIVEUP_MS`
  (`GpuOrderedWait` sites are under `Enabled()`). **`GOW3_SUBMIT_AHEAD` is also read by decode-pacing**
  (gow3_decode_pacing.cpp `SubmitAheadOption`, same default 2), which the Deck preset turns on
  (`GOW3_DECODE_PACING=1` in DECK_SWITCHES): setting it for a U5-2 test changes decode-pacing too. With fences on,
  `PacingOnDecode` wins in `sceGnmSubmitDone`; decode pacing paces only without it (fences off, or fences
  with `GOW3_SUBMIT_LOCK=gpu`).

## Interactions

- Do not combine with W3 / W3b (copy-ordered deferrals could overtake GPU-ordered labels). `GOW3_ASYNC_FENCES` and the
  `RecorderFences` / `AsyncFences` bits do not apply to these fences; recorder-lean does not touch them.
- decode-pacing is the same `decode` pacing kept under the copy model (stream order on stage B instead of the GPU).

## Evidence

- Deck A/B (`0771a23`, 67%, GPU auto): A fences off 64.0 FPS; B0 (ahead 0) 39.4; B2 (ahead 2) 41.2 (-36%). Game's EOP
  wait 6.2 -> 17.6 ms, WAIT_REG_MEM 5.9 ms a frame, stage B busy 80 -> 55%, submits 2.0 -> 10.8 a frame. Correct:
  fence lag 15 -> 0.4 ms, no crash or watchdog, 0 labels to unmapped memory, guest memory flat.
- The user: frame generation steadier, CPU use about halved, VRAM ~1 GB lower with fences on.
- Pinned 1,600 MHz: B2 ~+20 FPS over B2 auto, but the heavy graveyard view is still behind A (the user); GPU ~40%.

## History and pitfalls

- Dropped: MediEvil's UE4 waits once a frame on the newest frame's EOP, so with GPU-ordered fences CPU and GPU
  alternate (frame = CPU + GPU, not the max); the ahead-2 overlap is barely used (1-4 of ~850 submissions waited).
- Retry only together with removing that wait (find what the per-frame EOP, GraphicsCore ident 64, protects; a
  hybrid U5), as the user proposed. Code stays behind the opt-in switch.
