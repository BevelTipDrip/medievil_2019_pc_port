## What it does

Reverted the same day; the code is gone. It changed `Scheduler::WaitHostCopies` to call `KickRecording(true)` again
every 256 spins of its yield loop, not only once before the loop. That way host copies recorded after the first
kick would still reach the recorder. It was a symptom fix for H1 (the game frozen on its last frame).

## Invariants

- Today `WaitHostCopies` kicks once (`KickRecording(true)` before the wait) and then waits. That is correct only
  because no other thread records into the chunk during the wait. L5 makes that true: `ProcessCommands` drains
  stage B before every queued command. If L5's drain is removed, the H1 hang (and the C1 crash) can come back.
- A re-kick from a waiting thread can hand over another thread's half-recorded chunk. Do not add one again unless
  the wait runs on the only thread that records.

## Interactions

- L5 removed the cause (stage A ran queued commands beside stage B). With L5 in place, L4 had nothing left to do.
- The two-stage pipe (lineage-draw-pipe) is what makes two threads record at once. With `GOW3_DRAW_PIPE=0` there
  was no hang (T-race).

## Evidence

- H1 snapshot (cdb, run i2-profile-4k): `host_copies_issued` 0x7a4fdf against `host_copies_done` 0x7a4fd6, so 9
  copies never ran. `recording_owner` was stage B, and its chunk held 17.9 KiB that nobody handed over. The recorder,
  stage B and the copy threads were all idle.
- Build `684cd8f` (run i2-profile-4k-2): no freeze in ~4 minutes, but C1 crashed. That one run does not show whether
  L4 worked.
- T-race (`GOW3_DRAW_PIPE=0`, ~9 min) was clean, and so was T-L5 with L5 instead of L4 (~19 min, no fault). The
  user: "a pretty long run, no crashes". The user has not confirmed L4 itself in game.
- The H1 write-up planned a "Test T-H1" for L4 (several long sessions); it was never run. The T-H1 in
  plan-frame-pacing.md (host-map stats, build `2618b9c`) is a different test, and so is the T-L5 in
  plan-stage-b-split.md (newest-frame mode).

## History and pitfalls

- The revert message (`a07f709`): under the race, the re-kick handed stage B's chunks to the recorder after
  `SyncRecording`, into a command buffer that was being ended. That could turn the hang into a crash.
- Bloodborne's `WaitHostCopies` has the same single kick. Bloodborne fixed the root cause (0.3, `4d4d208`), which
  is the fix L5 ported.
- Only worth retrying if a hang shows host copies stuck in a chunk while only one thread records. Find that
  thread's missing kick instead of adding a re-kick to the wait.
