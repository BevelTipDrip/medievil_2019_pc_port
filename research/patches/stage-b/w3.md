## What it does

With `GOW3_WRITEDATA_DEFERRED=1`, `RunWriteData` on stage B copies a small WRITE_DATA (1-64 bytes, ending below
0x10'0000'0000, i.e. user memory, not direct memory where GPU resources and labels live) into a 64-byte payload. It
hands the write to `SignalAfterHostCopies`, so the recorder makes it after the deferred fences, in order. Stage B no
longer waits in `WaitDeferredSignals` for it. Off by default since `807d4c8`.

## Invariants

- Class C: it assumes nobody needs the flags at once. The guest and stage A's WAIT_REG_MEM must tolerate the value
  landing late, as they do for E1's labels. Who reads MediEvil's two flags is unknown (study-fence-waits P4).
- The branch returns before `WaitHostCopiesFor` (B1). That is safe for B1's rule because the deferred write runs
  after every copy queued before it (`Gow3Copy::AfterCopies`). Copies issued after the packet on the copy threads can
  still read the page before the deferred write lands, and so see the old value [inferred from the code]. Assumed
  harmless for "done" flags no GPU work reads.
- The address test is the only class filter. A small WRITE_DATA into user memory that the GPU must see in stream
  order would be wrong with W3 on. Writes into direct memory are not taken and still wait: on the PC the 8-byte
  `0x30000000a0` (value 0, twice a frame, ~0.03 ms) stays synchronous.
- Only the graphics queue's `RunWriteData` has the branch; the compute queue's WRITE_DATA always waits.
- The deferred write is a plain memcpy run on the recorder or the copy thread that finishes the last earlier copy
  (`Gow3Copy::AfterCopies`); it must not grow into anything that runs guest code (W3b).
- It needs RecorderFences on and stage B. Otherwise the synchronous path runs.

## Interactions

- W3b was built to remove the flip wait that W3 created. It deadlocks; do not combine.
- E1 is the same deferral for end-of-shader labels, and the one that was kept.
- B1: W3 bypasses the targeted copy wait (above).
- `GOW3_GPU_FENCES` (U5-2) is checked after W3's branch. With both on, W3 takes the write.

## Evidence

- T-W3 (WriteData targets, 2026-10-20): `0x6d2a4c88` / `0x6d2a4c90` (4 B, value 1, once a frame each) waited ~0.45 ms
  each. (The T-W3 in plan-frame-pacing.md, the 2026-10-19 wait sites, is a different test.)
- T-W3b (`2c2c4ba`, sections): `RunWriteData` 0.187 -> 0.013 us a packet, but `SignalFlip` 0.038 -> 0.28-0.46 and
  ordered tasks 0.30 -> 0.68. The wait moved to the flip. The user: no issues in loads or menus.
- T-W3d (`807d4c8`, no stats, heavy area): W3 on ~175 FPS, 1% ~120, 0.1% ~100; off ~175 / ~148 / ~124 standing.
  "W3 stays off."
- Deck task split (2026-11-04, W3 off): WRITE_DATA 0.85 ms a frame, all of it waiting (`wdata_wait`, the two "done"
  flags a frame; on the Deck they sit at `0x399e2418` / `0x399e2420`, study-fence-waits P4). Rescore A7: -0.3 to +0.5 ms on the Deck ("the same recorder catch-up wherever it is taken").

## History and pitfalls

- The wait is the frame-end recorder catch-up. Moving it (W3, W3b) only shifts it; T-W3c showed the present needs
  the recording caught up anyway.
- Worth retrying only with a design where stage B does not wait for that catch-up at all: the present recorded in
  stream order by stage B ("WRITE_DATA without stage B waiting" is the open Deck design item). Never set
  `GOW3_FLIP_DEFERRED` alongside it.
