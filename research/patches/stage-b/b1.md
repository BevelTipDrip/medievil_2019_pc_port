## What it does

Every deferred host copy (an upload from guest memory run later by the recorder or the copy threads) notes the
guest range it reads (`NoteHostCopySource`). The table has 4,096 slots of 64 KiB granules; a slot that two pending
granules share becomes a wildcard. A note of 64 granules or more sets `host_copy_big_seq`, which matches everything.
A command processor WRITE_DATA (`RunWriteData`, the compute queue's `WriteData`) calls `WaitHostCopiesFor`: it waits
only when a pending note overlaps the written range. Fences still wait for all copies.

## Invariants

- Every path that defers a copy reading guest memory notes its source before the copy can run. Today there are four:
  `SmallGuestCopy` (which covers both its `RecordHostCopy` and its `Gow3Copy::QueueCopy` branch; its inline branch
  off the recording thread needs no note), the `Gow3Copy::Async` in `ObtainBufferForImage`, and the grouped
  `Gow3Copy::Async` paths of `UploadDirect` and `UploadCopies`. A new site without a note lets WRITE_DATA change
  bytes a copy has not read yet: the GPU gets the new value instead of the old one.
- Notes take guest addresses. `UploadCopies` notes `copy.dstOffset` before it subtracts `arena->cpu_addr`. Noting
  after that line would put arena offsets in the table.
- A note stays pending while its seq is above `host_copy_sources_done`. Only `WaitHostCopies` raises that value,
  and only to the seq it read before waiting (the `Forget` guard). Notes made during the wait stay pending.
- Every check takes `host_copy_sources_mutex` (the patch audit's cost, a lock per range). Answers may be too
  cautious (wildcards, big notes) but never too lax.
- Only WRITE_DATA uses the targeted wait. A fence can tell the guest the GPU is past its work, so fences keep
  `WaitHostCopies` (the Bloodborne reasoning in `vk_scheduler.h`).
- `Rasterizer::WaitHostCopiesFor` (`vk_rasterizer.h`) drains the draw pipe before the check, as `WaitHostCopies`
  does. A caller that goes to the scheduler directly must already be the thread that records (stage B, or stage A
  with the pipe drained).

## Interactions

- W2 (caches) calls `WaitHostCopiesFor` once per queued readback range and once per image waiting for download
  (`texture_cache.cpp`, under `GOW3_EOP_TARGETED` / bit 60), and relies on this table. Toggle bit 62 is checked
  inside `WaitHostCopiesFor`, so setting it also makes each of W2's calls a full wait. Bit 62 alone is therefore not
  a B1-only A/B (from the code). With nothing queued, W2 makes no call and still does not wait.
- B1 skips only the copy wait. `RunWriteData` (and the compute queue's WRITE_DATA) then call `WaitDeferredSignals`,
  which waits for every deferred fence (E1's and the end-of-pipe labels), and each of those runs after the copies
  queued before it. That wait is what WRITE_DATA still costs (T-S1c: ~260 us a call), and what W3 tried to remove.
- W3 (opt-in) defers the whole write behind the copies and fences and skips this check.
- The host-copy deferral itself is part of the two-stage pipe and the recorder (lineage-draw-pipe,
  lineage-recorder-fences).

## Evidence

- T-B1 (build `a2a81fe`, heavy view ~2,830 draws): 130-132 FPS, worst frame ~12 ms. Of the 115-123 waits a frame
  only 1 was skipped, so WRITE_DATA is not where MediEvil's host-copy waits come from. The user: "1% lows higher on
  average in lighter areas, but the frame time spikes longer". The log has no measure of spike length.
- T-U1's bit 62 A/B never took effect, because `GOW3_TOGGLE_FILE` was not set.
- Deck baseline 1 (live, `5764607523034234880 0` = bits 60 + 62, W2 and B1 both off): 70.2 vs 74.2 FPS, stage B
  96.5% busy, stage A waited 42%. That -4.0 FPS is the largest live gain measured on the Deck, but it is W2's and B1's together. The
  user reported no visual issues.

## History and pitfalls

- Ported from Bloodborne (#1 of its list). At first it was kept as "harmless, correct". Its value came later,
  through W2 reusing the table.
- The spikes the user saw in T-B1 were never resolved (patches-and-pr-proposal.md). Same-launch A/B tooling came
  later, and a live A/B of bit 62 at a spike spot was planned and never run.
- Bit 62 meant L1 (region caches) before T-B1. Docs older than T-B1 that mention bit 62 refer to L1.
