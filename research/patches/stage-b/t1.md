## What it does

The texture-set memo takes only stages with images, so every stage without one (most vertex shaders) went through
`BindTextures`' slow path. That path zeroes the resolved array, sets proxy flags, queries the registry and scene,
and runs the stats timer, all for images. With an empty `stage.images` it now does only what the slow path really
does with an empty list: clear `image_bindings`, `image_binding_entries`, `image_desc_overflow` and
`image_desc_storage`, bump `bind_epoch`, and call `BindSamplers`. Second toggle word 131072 sends these binds
through the slow path again, live. deck-lab only.

## Invariants

- The fast path must stay an exact copy of the slow path's effects for an empty image list. If the slow path gains
  a per-call reset or another side effect that also applies without images, add it to the fast path too. Otherwise
  stale bindings leak into the next stage's descriptors.
- It sits after the memo attempt (`BindTexturesFromSet`), which returns before taking a set slot when `count == 0`.
  So the slow path's `texture_set_unkept` / `KeepTextureSet` handling has nothing to do here. Moving it before that
  call is fine only while that stays true.
- `BindSamplers` must still run: stages without images can have samplers bound on their own.

## Interactions

- One of the Deck's four per-draw cuts (with R1-region-index, R2 = R2-residency-bitmap and T2), measured together.
  (The runtime card `R2`, rwlock handles, is a different patch.)
- The "texslow" section and the slow-bind statistics no longer include these binds (they stay in "textures"). So
  the slow-path numbers before and after `a8b0c13` are not comparable.
- T2 sends stages without a prepared draw through the memo, but it too only applies when there are images.

## Evidence

- Cuts redo (2026-11-07, draw preparation alive): R1/R2/T1/T2 off (983040) +3.8 points of a core at the 60 cap (stage B 50 -> 53%), +0.17 W CPU; uncapped 82.8 -> 81.7 FPS, presents > 15 ms 54 -> 89 a minute, worst 20.4 ms. Launch 15's +14.6 was inflated: with no prepared draws every draw took T2's path.
- Before: ~970 binds a heavy Deck frame, "memo off or no image" at ~0.18 us each (stats timer included).
- Deck `deck-perdraw-1.log` (all four cuts `0 0` vs off `0 983040`, 30 s x 4): 78.8 vs 78.2 FPS, stage B busy 86.7
  vs 92.6% (~0.75 ms a frame freed). Stage B then waited on stage A and on the GPU more. T1 counted ~920 binds a
  frame. With single bits off (20 s x 3) the FPS was 78.7-79.0, within noise, so T1 has no measurement of its own.
- Not verified in game on its own. The commit says it is exact by inspection.

## History and pitfalls

- After these cuts the limit moved: stage A and the power-capped GPU now gate stage B about as much as its own work
  does. Further per-draw cuts on the Deck need stage A cheaper as well.
