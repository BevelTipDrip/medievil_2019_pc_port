## What it does

`GOW3_OCCLUSION=1` (needs `hostQueryReset`; the game also needs `r.AllowOcclusionQueries=1`): each `ZPASS_DONE`
(`PixelPipeStatDump`) goes to stage B in order with the draws (`Rasterizer::OcclusionEvent`) and ends a chain of
Vulkan occlusion query segments (one active while a render pass is open, via `Scheduler::RenderPassHook`). A
completion thread (`gow3:Occlusion`, `CompletionLoop`) waits on the timeline semaphore for the submission holding
them, reads the segments, sums them in order and writes each event's running total into the game's memory
(`WriteCounters`: first depth block gets the total, others 0, all with the valid bit). O3 (`b6dfc40`, `cdb43af`): a
pass end sets `submit_wanted` once the oldest unsubmitted event is `GOW3_OCCLUSION_SUBMIT_US` old (1000; 0 off), and
stage B submits before its next command (`BeforeRecord` -> `TakeSubmitWanted` -> `Flush`). Off (or no
`hostQueryReset`, or an event with 0 pairs: `OcclusionEvent` returns false): the port writes "visible".

## Invariants

- Never wrongly hidden: a segment without a free slot (16,384 `NumSlots`) or a failed result counts as 2^32 samples.
- A begin event (16-byte aligned) clears its begin and end counters first, so an earlier use never reads valid early.
  The clear covers at most 16 depth blocks (a 256-byte zero buffer, `min(pairs * 16, 256)`); more pairs would leave
  stale valid bits past the 16th.
- Totals are written in event order and only after the GPU finished every segment before the event; a missing
  result blocks all later ones (a freeze, not a stall).
- **Class C:** our depth at query time must match the PS4's, or objects pop or vanish (none seen in T-O2b / T-O2c).

## Interactions

- Superseded by hzb-remap (HZB occlusion served from finished readbacks, no wait on the frame); occlusion-queries-off
  turns the game's queries off where the remap cannot run.
- R4a (`r.NumBufferedOcclusionQueries=2` alone, 94 -> 75 FPS) is the same render-thread wait, with fake results.
- D3 came out of T-O2d's wait list (write-fault downloads waiting on `Finish`).

## Evidence

- T-O2b: 39-63% hidden, results 7-9 ms after the event; 86-89 FPS (render thread waits for last frame's results).
- T-O2c (buffered 2): 168-192 FPS (T-O1 126-135) but the user: "the 1% lows are slightly worse ... probably 15-20%".
- T-O2d (buffered 3): latency event -> submitted 2.6-3.0 ms, -> GPU done 4.8 ms; "lots of large spikes".
- T-O3 (submit at every query pass): ~128 submissions a frame, 126-129 FPS; the user: "about as bad as they've ever
  been". T-O3b (rate-limited): ~1 a frame, results 3.4 ms, 181-185 FPS, the user: "Much better ...".
- T-O3c (buffered 2): still view 205-221 FPS, p99 5.4-6.0 ms; the user: "if I pan the camera at all the lows tank";
  a 58.4 ms frame in the same window as a 59.2 ms result (the game waited for an outlier). The panning slow frames
  themselves were stage B 85-97% busy with result latency 3.3-4.3 ms throughout: the doc reads them as stage B load
  (more draws and queries in view), "not occlusion latency".

## History and pitfalls

- Dropped: correct and culling up to 63-68%, but the game's render thread waits on results, which costs more than the
  culling saves while panning (T-O3c, fix-inventory section 10). The design (class `OcclusionQueries`, the segment
  chain, `Event(address, pairs)`) follows the Bloodborne port's `vk_occlusion.h` (0.5, `c7e3e55`), where a dispatch
  writes the totals into guest memory on the GPU; under the copy model the host must, so the completion thread and
  O3 are ours. Keep the design credit (code header) if the code moves.
- The T-O2 first launch hung after the intro skip (game threads locked, before O2 ran); not seen again.
- Retry only if the result wait goes away (results the game reads a frame later without blocking, as hzb-remap does).
