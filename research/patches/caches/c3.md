## What it does

UE4's render-target pool decommits a pass's targets while unused and commits them again when needed (MediEvil: the
first torch coming into view). `TextureCache::UnmapMemory` frees (or, since N-24, parks) the images and records their addresses in
`unmapped_addresses`; the next `FindImage` that creates an image at such an address flags it `ImageFlagBits::Undefined`.
A render or depth target binding (`BeginRenderingFull`, `FindRenderTarget`, `FindDepthTarget`) calls
`DiscardUndefinedContents`, which drops `Undefined` and `Dirty` without uploading. Any other first use goes through
`RefreshImage`, which drops `Undefined` and uploads guest memory as before.

## Invariants

- Only a render / depth target first use may skip the upload. `RefreshImage` must clear `Undefined` before its
  `Dirty` check, so a texture / storage / copy first use uploads guest memory (the Mausoleum fix and every CPU-loaded
  texture rely on it).
- `DiscardUndefinedContents` runs before `UpdateImage` at the colour target binding in `BeginRenderingFull`; moved
  after it, the upload happens first and C3 does nothing.
- `DiscardUndefinedContents` must not take `mutex` (some callers of `FindRenderTarget` / `FindDepthTarget` hold it,
  std::mutex: T-C3 hung at boot). It changes the flags with `std::atomic_ref<u32>` `fetch_and`, as `UpdateImage`'s
  fast path reads them atomically.
- `unmapped_addresses` is only touched under `mutex` (`UnmapMemory`, `FindImage`); it is cleared at 16,384 entries
  (losing marks costs an upload, never correctness).
- Toggle bit 61 is checked only where `FindImage` flags a new image: set live, it stops new flags, but an image
  already flagged still skips its upload at its first target binding.
- Assumption (class C): memory a guest unmap freed holds nothing a render target needs loaded before it is drawn.
  A pass that loads (blends over) a recommitted target would see garbage instead of the guest's bytes.

## Interactions

- new-images-undefined extends the flag to every new image, so with its default on C3's address set only decides the
  stats; toggle bit 61 turns both off (and the GPU-freed case of clear-skips-upload).
- park-unmapped: a parked target taken back is flagged `Undefined` through this same address set.
- pool-kept-pages: non-target first uses still upload guest memory, so they depend on recommits getting their own
  bytes back (or zeros), never another allocation's.
- P2 made the torch spikes visible (T-P2); C3 removed their cause.

## Evidence

- T-R1 here is the frame-pacing run of 2026-10-19 (not the boot-size T-R1 of plan-stage-b-split): per torch coming
  into view, 0x20a0000000 3840x2160 RGBA16F (64 MiB) and 0x2086000000 RGBA8 (32 MiB) uploaded again, worst frames
  19-20 ms.
- T-C3b: torch windows skip 64-288 MiB of uploads per 5 s; worst frames 7-11 ms (a few 15-18), p99 4.8-10 ms. Live
  A/B: off, the pair re-uploaded 3 times per window, worst 19.2 ms; on, no re-uploads, worst 7-12 ms. The user:
  "Massive improvement"; torches, glow and haze look as before. Verified in game.

## History and pitfalls

- T-C3 (`1024224`) hung at boot: the discard took `mutex`. `d9949cb` made it lock-free. Its commit notes a residual
  race: other flag updates are plain read-modify-writes under `mutex`, so a CPU write racing with the first binding of
  a new undefined target could lose its dirty mark (pool targets are not CPU-written then).
- The undefined-upload path was a Hilltop Mausoleum suspect and was cleared (`GOW3_NEW_IMAGES_UNDEFINED=0` run).
