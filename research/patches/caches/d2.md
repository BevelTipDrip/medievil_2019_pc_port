## What it does

The runtime keeps `gpu_written`, one bit per 4 KiB page below 2^40 (32 MiB, sparse), set by `ObtainBuffer` for written
bindings and cleared where a download, an unmap or D2b drops the GPU state (`runtime_memory_mark_gpu_written`,
`ForgetGpuWritten`). `guest_memcpy` / `guest_memset` / `guest_memmove` test the destination's bits
(`runtime_memory_precise_write`); a hit calls the hook into `BufferCache::PreciseCpuWrite`: the bytes are copied
aside, queued in `cpu_writes`, then written into guest memory through the backing view (past the page protection, no
fault). `ProcessCpuWrites` (`Rasterizer::BeforeRecord`, before each draw or dispatch is recorded, and at the start of
`DownloadMemory`) copies exactly those bytes into the arena. D2b (`GOW3_PRECISE_WRITE_RELEASE`, on): those bytes leave `gpu_modified_ranges`, and pages left with
no GPU-only bytes become ordinary pages again.

## Invariants

- Ordering: a write is queued under `cpu_writes_mutex` before it goes into guest memory; `DownloadMemory` takes the
  same lock, applies the queue first and holds the lock while writing guest memory. Either order breaks: a download
  overwriting newer CPU bytes, or the GPU copy missing them.
- `src` is copied into a local buffer before any lock (`src` may fault); a `memmove` overlap is safe for that reason.
- `ProcessCpuWritesLocked` must note the write tick (`WriteTicks().Note`, for D3), erase twins over the range, and
  invalidate the texture cache range; a range no longer GPU-modified is only marked CPU-modified (uploaded on use).
- A stale `gpu_written` bit only costs the slow path (the hook finds nothing GPU-modified and still writes); a missing
  bit means a fault, as before D2. Every path that sets `gpu_modified_ranges` must set the bit (only `ObtainBuffer`).
  Stale bits are normal: `ForgetGpuWritten` clears only pages wholly inside its range, and the twins' upload path
  subtracts changed runs without touching the bitmap.
- `Rasterizer::PreciseCpuWrite` declines (normal write, fault) when bit 63 is set or the range is not in the
  rasterizer's `mapped_ranges` (`IsMapped`).
- If `TryWriteBacking` fails the call returns 0 and the normal write faults; the queued copy is then redundant but
  carries the same bytes.
- Toggle bit 63 (live) sends every write down the fault path; it also disables D2b (no bit left for it).

## Interactions

- U2: `ProcessCpuWritesLocked` writes straight into a mapped arena when the blocks are free, else staging + GPU copy.
  The Deck preset sets `GOW3_ARENA_HOST_VISIBLE=0` (DECK_SWITCHES), so there every precise write is staged.
- D3 / gpu-write-twins / fault-page-download handle the writes D2 cannot see: the game's inlined copies
  (`guest+0x68e109`, `0x68e149`: `vmovups` loops) still fault.
- D1 and D2 both clear `gpu_written` on an unmap. perf-diag's write-fault sites (`537d86e`, `057afc6`) found the
  writers.

## Evidence

- T-D2: write-fault downloads came from the CRT's `memcpy` / `memset` called by the runtime's guest wrappers.
- T-D2b: synchronous downloads 0 (was ~27/s); heavy view FPS 114-121 -> 119-127, stddev 1.1-1.5 -> 0.34-0.68 ms, p99
  10.9-13.0 -> 8.8-9.8 ms. The user: "The 1% lows are much more stable looking at the heavy long distance area, a
  significant improvement." T-D2c live A/B: "D2 definitely stays in." T-D2d (D2b): downloads 0, stddev 0.32-0.48 ms,
  p99 8.6-9.5 ms; the user: "the frametimes look great". Verified in game.
- Deck (study-deck-patch-audit row 53): 0-4 precise writes a second; cost one bitmap load per guest memcpy.

## History and pitfalls

- T-D2c: with D2 alone the kept GPU-modified state covered bytes the CPU had rewritten, so the inlined copies faulted
  5-10/s, more than with D2 off: D2b fixed that. Switching bit 63 on mid-run makes all such pages fault at once.
- The idea is the Bloodborne port's `NotePreciseUpload`, no code taken: Bloodborne learns of a write afterwards (no
  page protection); here it must come before the write. Not the Deck's D2 (D2-gettid).
