## What it does

MediEvil renders its translucency lighting volumes (64x64x64 RGBA16F), the volumetric fog grid (240x135x64) and the
colour grading LUT slice by slice as a 64-layer 2D render target and samples them as 3D textures. `ResolveOverlap`
used to `ExpandImage` on every switch in either direction, each a full re-upload from guest memory. Now a 2D render
target with one layer per depth slice of a same-sized 3D image (`IsVolumeSliceTarget`) returns the 3D image itself
and renders through a 2D array view of it; 3D images are created `e2DArrayCompatible`. `FindImage` no longer frees
the volume as "picked up wrong" (1 layer < 64).

## Invariants

- `IsVolumeSliceTarget` must stay this narrow: binding is `RenderTarget`, volume `Color3D`, request not 3D, equal
  width / height, request layers == volume depth, one mip on both sides, `IsVulkanFormatCompatible`. A wider rule
  (storage writes, mips) would hand back an image whose views do not exist for that use.
- A 2D array view of a volume carries attachment usage only (`ImageView` ctor: `eColorAttachment |
  eAttachmentFeedbackLoopEXT`); a sampled / storage 2D view of a 3D image is invalid without
  `VK_EXT_image_2d_view_of_3d` (upstream issue #18).
- Barriers on a volume cover the whole image: `Image::GetBarriers` forces layer 0 / count 1 (depth slices cannot be
  selected). Two such blocks exist now (upstream's and ours); both must keep the layer range at the image's.
- Clears of a `Color3D` image go to `ClearVolumeSlices` (an empty render pass on a 2D array view of exactly the
  slices), not `clearColorImage`. The `is_volume` layer-0 block left in `ClearImage` is now unreachable.
- Both switches gate the `ResolveOverlap` path: toggle bit 58 (live; also gates `FindImage`'s keep) and
  `GOW3_VOLUME_VIEWS=0` (read once, upstream's name).

## Interactions

- upstream-volume-views: upstream 1.3.4 reached the same idea independently (sampled views, its own switch,
  `ClearVolumeSlices`, 1.3.5 AMD fallback). The merge (`b7b78fb`, its message names the conflict) kept our view rule
  and their exact slice clears, and dropped upstream's `Is2dViewOf3dSupported()` condition on the slice path (our view
  is attachment-only); upstream's no-extension rule stays in the `ImageView` ctor and also strips the feedback-loop usage.
- texcache-stats: `GOW3_TEXCACHE_STATS` counts "volume views" and the expands this removed.
- Not related to the "V3" effect issues of plan-baseline-issues.md (2026-10-31; fixed by particle-bounds and the
  single pass off): same letter, different list.

## Evidence

- T-C1 (fix off): 9,760 expands = 9,760 uploads = 31.3 GB per 5 s in game (~6 GB/s over PCIe), 97 FPS; menu 7,200
  expands, 10 GB per 5 s. The fog grid alone 976 expands = 15.6 GB per 5 s.
- T-V3: expands 0 per window; map / level select ~70 -> ~200 FPS (stats 183-198); heavy view 97 -> 115-123 FPS,
  uploads 31 GB -> 0-15 MiB per 5 s, 1% lows ~60 -> ~100. The user: main menu ~240 FPS, level "fairly good".
- Fog A/B (same build, bit 58 twice): the user, "I see no difference, fog is definitely present with the fix on";
  off brought back ~10,500 expands / ~33 GB per 5 s. Verified in game.

## History and pitfalls

- A partial-slice clear first cleared the whole volume (a warning was logged); upstream's `ClearVolumeSlices`
  replaced that. A storage-bound 2D side of a volume is still not covered (would show as expands).
- The validation-layer run planned for the view / barrier rules was never done (patches-and-pr-proposal.md item 11,
  plan-upstream-merge.md: "pending since V3"); the views are valid by spec reading only, untested on AMD / Intel.
- The same ping-pong exists in the Bloodborne port's `ExpandImage` / `ResolveOverlap` (identical code, T-C0).
