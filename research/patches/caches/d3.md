## What it does

`GpuWriteTicks` keeps the submission tick of the newest GPU write per 64 KiB page (1 MiB pages for writes over
16 MiB) in lock-free sparse tables below 2^40, noted by `ObtainBuffer` for written bindings and by D2's
`ProcessCpuWritesLocked`. `DownloadMemory` takes the newest tick over its copies; with a tick and a readback queue it
waits for that submission only (`Scheduler::Wait` when it is still queued) and `FastReadback::Copy` copies on a queue
of a compute-only family, waiting on the timeline semaphore at that tick, instead of `scheduler.Finish()` behind
every queued frame. `Instance::CreateDevice` picks the first family with compute and without graphics; sparse arenas
become `eConcurrent` across both families (`buffer.cpp`).

## Invariants

- Every GPU write into the arena must note its tick: today `gpu_modified_ranges.Add` exists only in `ObtainBuffer`,
  which calls `WriteTicks().Note`. A new GPU write path that marks memory GPU-modified without a tick, or a write
  newer than the noted one, would let the readback copy data the GPU has not finished writing.
- Tick 0 (none known) or no readback queue falls back to the old path (copy on the graphics queue + `Finish`).
- `FastReadback` is one shared object with one command buffer and fence and no lock of its own: calls are serialized
  only because `DownloadMemory` holds `cpu_writes_mutex` (D2) for its whole run. Moving the copy out of that lock
  needs a lock or one `FastReadback` per thread.
- Arenas must stay shareable by both families (`eConcurrent` when `GetReadbackQueue()` exists); an exclusive arena
  read by the second queue is undefined behaviour.
- `GOW3_READBACK_QUEUE=0` is read at device creation (no second queue, arenas exclusive) and in
  `FastReadback::Available`; `gow3_settings.cpp` also reads it to show `perf_gpu_data_no_waits` in the menu.
- `GpuWriteTicks::Note` stores the tick (no max, unlike U2's `GpuUseTicks`): an older note after a newer one would
  lower it. Notes come from the GPU side only (`ObtainBuffer`, `ProcessCpuWritesLocked`; a fault off the GPU thread
  is sent there by `ReadMemory` through `SendCommand`), in an order the draw-pipe drain keeps, so ticks only grow
  [inferred]. A note from another thread would need a max.

## Interactions

- gpu-write-twins and fault-page-download read the same `WriteTicks().Newest` to decide whether a page's GPU bytes
  are finished; D3 is their tick source. The ticks are noted with or without the readback queue; only the no-wait
  copy needs the queue (without it every download, a finished page's too, copies on the graphics queue + `Finish`).
- D2: its arena copies note ticks, so a download sees them.
- perf_gpu_data_no_waits=0 sets `GOW3_READBACK_QUEUE=0` together with twins, E1 and W2 (one launcher toggle).
- Plan-frame-pacing calls the idea R5 (Bloodborne's readback queue).

## Evidence

- T-D3b: D3 took every write-fault download (9-20 a second in the light view), but each still cost ~2.8 ms (max
  3.3 ms): the shader wrote those pages in the frame still being recorded, so the wait is for that submission. The
  user: "Still some fairly large dips I don't recall being there previously." Kept: each wait is now for its own
  write only; the remaining waits led to gpu-write-twins.
- Deck (study-deck-patch-audit row 10): on, downloads ~0/s. No live A/B of D3 alone on either platform.

## History and pitfalls

- Port of the Bloodborne port 0.3 (`GpuWriteTicks`, `FastReadback`, GPL-2.0-or-later, credited in the commit).
- Needs a compute-only queue family; on a GPU without one the code silently keeps the old path ("Readback queue:
  family N" is logged only when found).
- The light-view dips seen in T-D3b were across runs and spot-dependent (T-O1 caught quiet windows); not a D3
  regression proven by an A/B.
