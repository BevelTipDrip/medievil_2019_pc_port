## What it does

`TextureCache::ProcessDownloadImages` (every end of pipe on stage B, deferred readbacks on) used to wait for every
host copy (`Scheduler::WaitHostCopies`) so that upload workers stop reading pages before readbacks write them or
downloads protect them. W2 collects the ranges that matter, under `readback_mutex` and `download_images_mutex`: every
queued readback (`pending_readbacks.ForEach`) and every image about to be downloaded (`download_images`). With the
locks released it calls `WaitHostCopiesFor` per range; B1's host-copy source table answers whether a copy may still
read it. Usually none does, so there is no wait.

## Invariants

- The range list must hold every readback that `RetireReadbacks` below may write into guest memory and every image
  that will be downloaded (and page-watched) in this call. A range left out lets a copy thread read memory while it
  changes (R1-stale-eop's black torch boxes came from dropping that protection).
- The ranges are collected under the locks and waited for without them: a copy thread faulting on a watched page
  resolves readbacks under `readback_mutex`, so waiting with it held can deadlock.
- `WaitHostCopiesFor` depends on B1: every deferred host copy must note its source (`NoteHostCopySource`). With toggle
  bit 62 set (B1 off) each listed range does a full wait, and an end of pipe with no ranges does not wait at all.
- Toggle bit 60 turns W2 off live (full wait); the same bit also turns P2 off. `GOW3_EOP_TARGETED=0` at start.
- Only inside `if (deferred_readbacks)`: `GOW3_DEFERRED_READBACK=1` (off when unset; `graphics_options.py` and the
  launcher, Deck preset too, write ini `deferred_readback=1`). Without it `ProcessDownloadImages` takes the old
  per-download path and W2 / P2 do nothing.
- The guest's fence order does not come from this wait: on stage B the label is written by the recorder after the
  queued copies (lineage-recorder-fences).

## Interactions

- depends_on B1 (targeted `WRITE_DATA` waits) for its source table; B1 + W2 are the Deck's "targeted waits".
- E1 (end-of-shader fences deferred): without E1, W2's saved wait moved to the end-of-shader event's full wait
  (T-W2); with E1 it became a gain, which made W2 the default (`852ec13`).
- supersedes P2: with no readback work the range list is empty and W2 waits for nothing, which is what P2 did
  (study-deck-rescore-rejected A12).
- perf_gpu_data_no_waits=0 sets `GOW3_EOP_TARGETED=0` with D3, twins and E1.

## Evidence

- T-P3: the full wait was 21.0% of stage B's samples. T-W2 (queries on): the wait gone, ~600 ms per 5 s less
  waiting, but FPS unchanged; the user: "No real improvement to the 1% lows while panning". T-W2b (queries off): no
  visible difference either way; kept opt-in then.
- T-E1 (E1 on), A/B of bit 60: ordered tasks 0.23 vs 0.49-0.51 us per packet, packet 2.03-2.06 vs ~2.15-2.2 us,
  stage A blocked on copy threads 0% vs 6-12%; FPS and p99 within noise (126-139 vs 129.5-136, p99 8.2-9.7 vs
  8.4-9.6 ms). The user, about the run (E1 + W2), not the bit-60 A/B: "1% lows in light areas seem really good, I'm
  seeing 220 FPS with 200 1% lows".
- Deck baseline 1 live A/B (word 1 = bits 60 + 62, W2 and B1 off): 74.2 -> 70.2 FPS, stage B 96.5% busy: +4.0 FPS
  for the targeted waits, the largest single gain measured live there. No visual issues reported.

## History and pitfalls

- study-deck-patch-audit row 45 suspected the per-range `host_copy_sources_mutex` would cost on the Deck; the A/B
  cleared it.
- Do not "simplify" by skipping the wait when readbacks are queued (R1-stale-eop, reverted: V2 black torch boxes).
