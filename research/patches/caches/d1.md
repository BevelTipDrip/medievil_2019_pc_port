## What it does

`Rasterizer::UnmapMemory` sets the download reason `Gow3Stats::Unmap` (`DownloadReasonScope`) before invalidating
the buffer cache. In `BufferCache::ReadMemory` that reason no longer downloads the GPU's data (a full GPU wait,
~4 ms): the range leaves `gpu_modified_ranges` and the `gpu_written` bitmap, is unmarked GPU-modified and marked
CPU-modified, and `unmap_discards` counts it. The next use uploads whatever the guest put there.

## Invariants

- Only the `Unmap` reason may discard: the reason is a thread-local set by the scope in `Rasterizer::UnmapMemory` and
  captured by value into the flush lambda (it runs on the GPU thread via `SendCommand`). A discard on a write or read
  fault would lose real GPU output.
- The discard must clear every trace of GPU ownership together: `gpu_modified_ranges.Subtract`, `ForgetGpuWritten`
  (D2's bitmap), `UnmarkRegionAsGpuModified`, `MarkRegionAsCpuModified`. Twins over the range are erased just before
  (gpu-write-twins), also when bit 56 is set. A partial clear would leave a page that faults or downloads into a dead
  range. `ForgetGpuWritten` clears only pages wholly inside the range; an edge page keeps a stale bit (D2's slow path
  only, harmless).
- Assumption (class C): the guest never reads back GPU-written data from memory it unmapped. On the PS4 (unified
  memory) a recommit at the same address would see the GPU's bytes; here it sees the bytes guest memory held before
  the GPU wrote [inferred].
- Toggle bit 56 restores the download, live.

## Interactions

- pool-kept-pages promises a recommit its own bytes back; for GPU-written buffer data D1 makes those the pre-GPU
  bytes, not the GPU's output. No MediEvil case is known (T-D1b: no unmap downloads at all).
- C3 / park-unmapped are the texture-cache side of the same guest unmaps (images freed or parked, never written back:
  upstream's "TODO: Download image data back to host").
- Mixed into `057afc6` with the download-cause counters ("Buffer downloads/s (GPU waits): read fault ... unmap ...;
  unmaps discarded"), which belong to perf-diag.
- Not the Deck's D1 (initial-exec TLS model, D1-tls).

## Evidence

- T-SF1: 3,950 synchronous downloads in the run, ~40 a second in the heavy view, up to 5.8 ms each, 10.0 s of waiting.
- T-D1b (build `057afc6`): every download was a write fault (25.8-27.4/s); unmaps 0, "unmaps discarded 0.0". D1
  never ran in MediEvil; the bit 56 A/B also never reached the game (the toggle file was not set by `run-game.ps1`
  then). Kept as correct and free. Not verified in game (nothing to see).

## History and pitfalls

- Built on the guess that UE4's constant pool decommits caused the downloads; the counters showed write faults
  instead, which led to D2, D3, twins and fault-page-download.
- With the toggle file not set, the T-D1b A/B compared identical builds (plan-frame-pacing correction after T-D2b).
