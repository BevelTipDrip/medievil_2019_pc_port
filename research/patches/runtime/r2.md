## What it does

Every PS4 rwlock call (`rw_init`, read / write / try / timed, `rw_unlock`, `rw_destroy`) checks its handle under the
one `registry_lock`. That check walked a linked list of every live rwlock. It now probes an open-addressing set of
pointers (`registry`, linear probing from `slot_of`, a Fibonacci hash of the pointer). The set stays at most half full,
counting live and deleted slots, and `reserve_locked` rebuilds it at 4x the live count. Holders, error codes and the
lock itself are unchanged. No switch: same behaviour, a different data structure.

## Invariants

- `registry_size` is a power of two, at least 64, and `(registry_used+1)*2 <= registry_size` holds before every
  insert. `create_locked` calls `reserve_locked` first. Without a free (NULL) slot, the probe loop in
  `find_slot_locked` never ends.
- Deleted slots hold `&deleted`, a private static. They must never hold `1`: `rw_destroy` writes `(Rwlock *)1` into
  the guest's handle, so a destroyed handle has to miss the set. `find_slot_locked` also rejects `&deleted` and NULL.
- A probe stops only at a NULL slot. A deleted slot is skipped on lookup and reused on insert (`create_locked`), so
  removal must never write NULL into a slot that later probes run through.
- `registry_used` counts live plus deleted slots and `registry_live` counts live ones only. A rebuild drops the
  deleted ones. Both are changed only under `registry_lock`, as are all `*_locked` helpers.
- `slot_of` masks with `registry_size-1`, so it is only valid after the first `reserve_locked`. `find_slot_locked`
  returns NULL while `registry` is NULL (lazy init through `acquire` on a zero handle).
- The set holds pointers only: a rebuild moves slots, never the `Rwlock` objects. `acquire` drops `registry_lock`
  while it waits on `r->native` and uses `r` afterwards; `r` stays valid because `rw_destroy` refuses (`EBUSY`)
  while `inflight` or `holders` is set. Moving or reallocating the objects in a rebuild would break that wait.

## Interactions

- R3 (pool free-page hint) was built, launched and measured together with this patch. T-R23's gain belongs to both.
- D5 and the region-table locks are a different lock (`runtime_memory.c`'s host `pthread_rwlock`), not the guest
  rwlocks this card covers.
- Not the Deck's R2-residency-bitmap (buffer cache) either: the same ID, a different round.

## Evidence

- WPR before (Graveyard, plan-frame-pacing.md): `find_locked` was 11.8% of the game's main thread.
- T-R23 (R2 + R3, build `2097554`, same Graveyard spot, windows of 2,600-3,100 draws): median FPS 81.2 -> 94.7
  (+17%), lowest window 71.3 -> 80.7, p99 median 16.7 -> 14.6 ms. In the trace `find_locked` is gone (main thread
  81.9% game code, was 71.6% + 11.8%). The user: "the 1% lows seem much much better. When looking at an area that
  previously dropped to 50-60 fps 1% lows, it's closer to 80."
- `tests/test_rwlock_registry.c` (manual build, its header gives the `cc` line; not part of `build.sh --test`): 5000
  locks through several rebuilds, own-lock errors, garbage / destroyed / freed handles, re-creation into deleted
  slots, lazy init, four threads. It passes on the new code and on the original list version.

## History and pitfalls

- The Bloodborne port's rwlock registry still walks a list (fix-inventory novelty check, 2026-10-20).
- A freed `Rwlock` whose address `calloc` hands out again makes an old stale handle validate as the new lock. The
  list had the same weakness, so this is not a regression.
- S1 (the silent exit with code 5) first showed on the first launch of this build. It was later traced to winpthreads
  `pthread_mutex_lock` on a garbage mutex, seen across builds: not this patch (plan-baseline-issues.md S1).
- Draft upstream PR 5 (patches-and-pr-proposal.md): applies cleanly, verified by the unit test.
