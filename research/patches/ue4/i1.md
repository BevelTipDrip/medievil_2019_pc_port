## What it does

UE4's PS4 display metrics and work area are computed once at boot (1920x1080 unless the 4K branch runs), so the
old live `r.SetRes` left the menus' gamepad hit-test area at 1080p (I1: navigation stopped part-way). Now
`graphics_options.output_environment` boots the game at the output size: 4K with a 3840x2160 VideoOut
(`GOW3_INTERNAL_WIDTH/HEIGHT`) and "4K display metrics at boot" (two `je` -> `nop`, the PS4 Pro's own branch); any
other size with a VideoOut of that size and the sized patch "Boot display size WxH" (`Type="size"` lines:
W and H over the rodata default rects 0x3cbe750 / 0x3cbe7b0). `9753e2f` split `render_resolution` into
`output_resolution` + `render_scale`. The windowed window opens at the image size (`FitWindowedSize`).

## Invariants

- Never both boot patches above 1080 lines: with a VideoOut taller than 1080 the 4K patch's hard-coded 3840x2160
  wins over the rect, so the non-4K branch removes `BOOT_4K_PATCH` from the selection.
- The VideoOut size must equal the booted size: the 4K branch only asks VideoOut "taller than 1080?"; the rect
  path needs `GOW3_INTERNAL_*` too, or window and swapchain disagree with the game's buffers.
- Above 1080p (by area) `POOL_PATCH` is always added, whatever the Patches tab says (it is `isEnabled="true"` there
  at every size anyway; a 3840x2160 target took a 64 MB buddy block and the stock 128 MB pool crashed).
- 1920x1080 adds nothing. `GOW3_UE4_BOOT_SIZE` other than `1` (read in `output_environment` only, so not in
  switches.tsv) sets `GOW3_UE4_SETRES` instead: upstream's live path, which brings I1 back.
  `GOW3_UE4_BOOT_4K=0`: 4K through the rect path instead of the PS4 Pro branch.
- `sceVideoOutClose` ignores an invalid handle (a refused second open must not close the game's main port).
- The addresses are per eboot (01.00 and 01.02 entries in MediEvil.xml); run.py applies them only to the eboot whose
  sha256 the profile knows (`patched`: `eboot_matches`, or `GOW3_FORCE_PATCHES`). `output_environment` runs before
  that check and does not know it: an unknown eboot keeps `GOW3_INTERNAL_*` (a WxH VideoOut) but gets no boot patch
  and no live `r.SetRes`, so it boots at 1080p in a larger VideoOut (breaks the invariant above; not tested).
- The pak still writes `r.setres` = output; it has no effect on the boot size (study-boot-resolution [V]).

## Interactions

- upstream-4k-framebuffer-pool: required above 1080p (both patch notes say so); output_environment forces it.
- upstream-ue4-setres: upstream 1.3.3 fixed #11 with a live `r.SetRes`; kept here only as the fallback, reached
  only through `GOW3_UE4_BOOT_SIZE` != 1 (not through `GOW3_UE4_BOOT_4K=0`, as fix-inventory section 7 says, and not
  for an unknown eboot). `GOW3_UE4_SETRES` and `GOW3_INTERNAL_*` are cleared when run.py finds no r.SetRes slot.
- live-render-scale: scale changes live; the output size is a restart (the boot rect is read once).
- finer-occlusion-culling is chosen from the same startup output size (`hzb_full_size_environment`, after
  `output_environment` in run.py).
- Deck preset: 1280x720 output -> "Boot display size 1280x720" (seen in `data/deck-baseline-1-ab.log`'s patch line).

## Evidence

- T-I1b (2026-10-18): the user, "that fixed the menu-bug for 4k output, it can be navigated now" (scripted run; its
  log was lost to a run-game.ps1 bug, so the log-side checks are unconfirmed).
- T-R1 / T-R2 (2026-10-25, 1440p): depth buffer 2560x1440 from the first frames; the user, "that worked, and menu
  navigation looks fine." T-R3 (3200x1800 at 67%): the user, "everything seemed to work as expected".
- 720p is in every Deck preset run; menu navigation there was not written up as a separate check.

## History and pitfalls

- Attempt 1 is lab change L3 (`ebf85f4`, opt-in); `c8615ea` made it the default, `601aec6` forced pool + 4K boot for
  4K native, `cbb3e91` added the rect patches (then three fixed sizes), `9753e2f` the one sized entry.
- T-B1 to T-D2b (2026-10-19) ran without the 4K boot patch because run-game.ps1 did not set it; the menus broke again.
