## The port's 01.00-only sites, mapped

Method (scratchpad `find_0102.py`, Capstone): each 01.00 site's instructions with rel branch targets and RIP
displacements masked, searched in the 01.02 code for one match; data through an instruction that references it.
Cvars (`cvars_0102.py` and the final pass): the UTF-16 name, the `lea rsi, [name]` that registers it, the object
from the `mov [rip+X], rax` after the constructor call (X = object + 8) or `lea rbx, [object]` + `mov [rbx+8], rax`;
the same rule reproduces all 18 01.00 objects in the table. Checked by compiling `src/hzb_hook.h` /
`src/level_hook.h` against both images (scratchpad `hooks_check.c`: both builds recognised).

## T-0102-5: the dust culled by angle (2026-11-01 20:16, RenderDoc, build `09af284`, log `data/t-0102-5.log`)

Same ini as t-0102-4, run under RenderDoc (`GOW3_RENDERDOC`); two F12 captures at the dust spot in Dan's crypt:
`research-data\renderdoc\dust_frame73172.rdc` (A, golden dust around the lectern and the right wall) and
`dust_frame74230.rdc` (B, a small turn later, no dust). Script `research-data\renderdoc\dust-analysis\rd_draws.py`
(every draw: shaders, targets, counts; final image) -> `draws-*.json`, `final-*.png`.
- A 648 actions, B 646. Draws only in A: **eid 4286, 96 indices x 7 instances into the 2880x1620 separate
  translucency target** (UE4's GPU sprite layout: 16 particles per instance, so 112 particles; the dust), eid 4346
  (one quad, the lectern's blue star, which twinkles), and a 6768-index mesh in the base and velocity passes.
- **B does not issue the dust draw at all**: the game's own visibility step drops the emitter on the CPU; the GPU
  path (depth test, the effects-resolution composite, the port's caches) never sees it. Occlusion is out:
  t-0102-3 ran with `r.AllowOcclusionQueries=0` (no occlusion culling at all) and the dust still vanished. Left:
  view-frustum culling by the component's bounds.
- **The asset**: Level_00_DC's `00_DC_MAIN_Lighting.umap` places `PS_air_sparkles` and `PS_air_sparkles_02`
  (also in 7 other levels). `PS_air_sparkles` (pakchunk0) is a GPU sprite emitter (`TypeDataGpu`) **without
  `bUseFixedRelativeBoundingBox` / `FixedRelativeBoundingBox`** in its name map (`_02` and `PS_HM_TombSparkles` have
  both). UE4 4.21 GPU emitters have no CPU particle positions: without fixed bounds their box is a bogus 1-unit box
  at the component's origin [recalled from ParticleGpuSimulation.cpp `UpdateBoundingBox`, not checked in the eboot],
  so the whole system is culled once that point leaves the view while its particles are still on screen.
- [I] So this is likely the game's own behaviour (same code and content on a PS4), not a port fault, though the user
  remembers it as new. Fix options: patch the GPU emitters' bogus box extent in the eboot (one constant once the
  function is found), or give `PS_air_sparkles` a fixed box in the override pak (needs new name-map entries).
